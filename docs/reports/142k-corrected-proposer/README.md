# #142K — Regenerate with the corrected proposer and measure proposal quality

**Final question.** After fixing the proposer semantics, how often does the model generate a valid
architectural proposal on its own, and can one bounded critic-informed regeneration close the remaining
gap without touching geometry?

**Answer.** With the corrected prompt, gpt-5 generates a critic-clean proposal **61.7% of the time**
(100 of 162, against 36.4% under the old prompt), a clean proposal that the unchanged production
pipeline realizes and validates **50.0% of the time** (81 of 162, against 31.5%), and **every one of the
20 briefs — B12 included — has clean passing proposals in its first batch**. The production gate
selects a passing plan for **20/20 on the first batch**; no critic-informed regeneration was needed.
The old semantic defects are gone: multi-door bathrooms 31 → 0, illegal wet-room entries 30 → 0,
access-vs-adjacency contradictions 17 → 0, exposure impossibilities 6 → 0, doors without walls 39 → 1.
What remains (62 invalid proposals) is 92% one rule the prompt never stated — a bedroom or safe room
opened directly off the living room — plus two genuine topology errors. The bounded retry path exists
and was exercised on the only all-invalid batch available (the OLD dataset's B12, §6); geometry,
validators and the critic are unchanged.

Data: `data/generation-dataset-142k.json` (every raw response, parsed JSON, usage, cost, timing,
prompt hash — the same record schema as the frozen #151 dataset, passes its `preflight`),
`data/analysis_142k.json` (per candidate: critic findings, score, production outcome; per brief: gate
selection and quality), `data/old-dataset-b12-retry.json` + `data/analysis_old_retry.json` (§6).
Figures: `figures/B*_142k_plan.png` (the 20 gate-selected plans).

## 6. One bounded critic-informed retry (task §5–§7)

Rule prototyped (`regen_142k.retry`): if a brief's batch has NO critic-clean proposal, summarise the
critic's HARD findings per rejected proposal (codes + details, no geometry, no edits), append them to
the same prompt, ask once for a completely new batch, run the same critic; a second all-invalid batch
returns `NO_VALID_PROPOSAL` with both rounds' findings. Never more than one retry.

**First-pass performance:** 20/20 briefs succeed on the corrected first batch, so the retry never
triggers on the new dataset. **After retry:** +0, nothing to add. To exercise the mechanism on a
real all-invalid batch it was run on the only one available — the OLD dataset's B12, under the OLD
prompt it was generated with (isolating the value of the feedback from the value of the prompt fix):

| | old B12 batch 0 (old prompt) | B12 retry batch (old prompt + critic findings, one call, $0.20) |
|---|---|---|
| proposals | 8 | 8 (0 schema-rejected) |
| critic-clean | 0 | **6** |
| HARD findings | ACCESS_SPATIAL_CONTRADICTION 3, EXPOSURE_INFEASIBLE 3, ILLEGAL_ACCESS_PAIR 3, UNREACHABLE 3, WET_ROOM_ENTRY_POLICY 1 | CONTACTS_NOT_REPRESENTABLE 2 (two proposals still state a clustering preference as required walls: a triple lens) |
| clean & production PASS | 0 | **5** (#0 #4 #5 #6 #7; #2 clean but EXPOSURE_INFEASIBLE in its family) |
| gate | NO_VALID_PROPOSAL | **PASS #0** (clean rank 0, access 9/9, spatial 15/15, circulation 15.6%, max aspect 2.12, 3/3 PREFERRED rooms exposed) |

So the critic's findings alone — fed back as text under the OLD prompt, no repair, no edit — turned an
all-invalid batch into a batch with 6 clean and 5 passing proposals in one bounded round. **First pass:
19/20 (old dataset) · after one retry: 20/20.** The same analysis of the old dataset with the
production critic reproduces #142J exactly (59 clean, 19 gate PASS), so the two datasets are measured
on one instrument. Feedback text and the raw retry response: `data/old-dataset-b12-retry.json`
(record B12, attempt 1, `retry_feedback`); `data/analysis_old_retry.json`.

## 7. Scoring observations (task §9)

Not changed in this task; recorded. Among the clean & PASS candidates of each brief, the top-scored
clean candidate (the gate's choice) is the best on circulation share or on worst-room aspect in only
9 of 20 briefs; in 11 it is best on neither. In 2 of 20 (B15, B16) the top-scored clean candidate
did not realize at all and the gate fell through. The POC score (`critic.score_topology`, corpus
priors) was built to rank topologies without geometry; now that only consistent candidates reach it
and most of them realize, it is the weakest link between "valid" and "good".

## 8. Recommendation — exactly one next bounded step

**Replace the heuristic pre-realization ranking of critic-clean candidates with a measured one: run the
unchanged pipeline on every clean candidate and rank the PASSing plans by existing realized metrics
(circulation share, room proportions, preferred exposure, door count), with the POC score as a
tiebreak only.** Cost: ~1 s per candidate, 8 per brief. Measure, as in §7, how often the top choice is
also the best plan, on both datasets. Fold in, as part of the same step's prompt revision, the one
missing sentence that explains 57 of the 62 remaining rejections: *a bedroom or safe room is entered
only from the hall or circulation, never from the living room, kitchen or another bedroom*
(`ALLOWED_ENTERED_FROM`, already the system's rule) — then regenerate once to confirm the clean rate.

## 9. Scope kept

No realizer, embedder, validator or critic change; no automatic repair (the retry generates a fresh
batch from findings, mutates nothing); no special case for any brief; the regeneration loop is
bounded to one retry and is not wired into production; scoring untouched; the old dataset untouched.
Tests: `tests/ai_harness/test_regen_142k.py` (response parsing in either shape; feedback is findings
only, deterministic, no geometry).
