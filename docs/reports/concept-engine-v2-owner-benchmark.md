# Concept Engine v2 — owner benchmark (Issue #78, CE2-4)

Per the ROOT Issue's owner requirements (2026-09-20): "measure quality, diversity, runtime and
realization success... Deliverable at the end: an ORGANIZED BENCHMARK for the owner... only then
the owner decides whether the new engine may influence the primary." This report is that benchmark.
It does not recommend turning the flag on — see the Recommendation section for why.

Methodology: `spikes/failure_log_sweep/concept_diversity_v2.py`, replaying every PLANNED case of
the frozen 432-context regression corpus twice (flag OFF, then flag ON, same context) via
`app.demo.service.generate_demo_design`. Numbers below are taken from the committed
`docs/reports/concept-engine-v2-diversity-report.md`, generated by the same script.

## Diversity (before vs after)

| | Flag OFF (Issue #75 baseline) | Flag ON (this Issue) |
|---|---|---|
| Briefs measured | 404 | 404 |
| Briefs with ≥2 circulation classes shown | 49 (12.1%) | 71 (17.6%) |
| Circulation classes ever shown | SPINE, FRONT_BAND, TWO_WING | FRONT_BAND, SPINE, TWO_WING |

**AC-2 (≥40% of PLANNED briefs with ≥2 classes): NOT MET.** See "Why 40% was not reached" below —
this is a measured, evidenced architectural ceiling, not a defect this child Issue's own scope can
close.

## Realization success

Of the briefs whose winning outline's generator output (`generated.candidates`, unchanged) genuinely
contains a candidate of a circulation class other than the primary's, `concept_engine_v2.
plans_per_class` successfully realizes and scores a verified alternative for the large majority
(measured on a 150-brief slice: 31 of 37 such briefs, ~84%, after the fix described below — see
"What changed during implementation"). The remaining ~16% are candidates that exist in the
generator's own list but fail validation on every attempt within the per-class budget
(`_PER_CLASS_ATTEMPT_LIMIT` = 3) — the same "solved but refused by validation" outcome the
flag-off path already has to handle for its own candidates.

## Runtime

Measured on the developer machine (M1 Pro), the same `tests/wallclock.py` convention every other
timing assertion in this repo uses:

- A representative multi-class brief (1BR/2wet, 132 m², SPINE+FRONT_BAND available): flag OFF
  0.53 s, flag ON 0.48 s (flag ON was NOT slower — `plans_per_class`'s bounded class search costs
  less than `_alternative_plans`'s up-to-8-attempt family walk on this brief).
- The heaviest PLANNED brief class in the corpus (6 bedrooms, 3 wet rooms — most candidates
  `concept_generator` produces for one outline): flag OFF 11.06 s, flag ON 11.10 s — a 0.04 s
  delta, noise next to the base multi-outline survey a brief this size already pays for.
- `CONCEPT_ENGINE_V2_MAX_REALIZATIONS` = 10 bounds the worst case theoretically (≈10 × ~165 ms per
  solver attempt, the same per-candidate cost `ALTERNATIVE_ATTEMPT_LIMIT`'s own docstring
  measured — ≈1.65 s) — consistent with what was actually measured.

**AC-4 (wallclock budget test passes, no-op under `WALLCLOCK_BUDGETS=off`): MET** —
`backend/tests/test_concept_engine_v2_budget.py`.

## LOST / GAINED / primary_signature_changes

Measured across the SAME 404-brief PLANNED set, flag OFF vs flag ON, same contexts:

- LOST (planned flag-off, refused flag-on): 0 (the primary's own realization path is completely
  untouched by this flag).
- GAINED (refused flag-off, planned flag-on): 0, for the same reason.
- primary_signature_changes (the primary's own rooms differ flag-on vs flag-off): 0, confirming the
  Goal's "the primary plan... stay[s] byte-identical."

**AC-1 (flag off — frozen corpus snapshot identical to base) and the ROOT's regression budget
(LOST 0, GAINED allowed, primary_signature_changes 0): MET** —
`backend/tests/regression_corpus/test_frozen_regression_corpus.py` (`TEST_MODE=REGRESSION`) passed
unchanged on this branch — the flag defaults `False`, so this suite never exercises the new path
at all; the separate flag-ON replay above (`concept_diversity_v2.py`) is the direct evidence for
the "flag ON changes nothing about the primary" half of the regression budget.

## Quality (M1-M6)

The primary's own M1-M6 quality metrics are, by construction, unchanged flag-on vs flag-off (the
primary is never re-realized by this Issue — same geometry, same `quality_metrics.measure_design`
result). For the ALTERNATIVES set: `concept_score.concept_score` (Issue #76) already incorporates
weighted M1 (bedroom/master aspect), M3 (circulation share), M4 (hall aspect/door count) and M5
(wet adjacency) components directly into the score `plans_per_class` selects the BEST candidate
by — so every flag-on alternative is, by construction, the best-scoring realization available for
its class on exactly those dimensions, not merely the first one found. A full before/after M1-M6
comparison ACROSS the alternatives sets (flag-off's family-nearest walk vs flag-on's class search)
was not run for this report — the two walks optimize for different things (area-proximity vs
circulation-class diversity) and are not directly comparable on M1-M6 without conflating "which
plan won" with "how good the winner is"; a follow-up could measure this directly against a
`concept_score` baseline if the owner wants it before a flag decision.

## Why 40% was not reached

`concept_engine_v2.plans_per_class` operates entirely WITHIN one `run_general` call — one outline,
one buildable region, `concept_generator.generate_concepts`'s own candidate list for THAT outline.
Measured directly (not inferred): of a 150-brief sample, only 37 (24.7%) had `generated.candidates`
containing so much as ONE candidate of a circulation class different from the primary's — the
generator's `_hub_concept`/`_front_band_concept` builders reject far more often than they accept for
a typical single outline (consistent with Issue #76's own finding that a realized HUB_LOBBY plan
never appears anywhere in the flag-off 404-brief baseline). No amount of search budget or
adaptation-ladder cleverness raises a candidate's availability past what the EXISTING builders
already decided for that outline — `plans_per_class` correctly realizes the large majority of what
IS available (see Realization success above), but the ceiling itself is architectural: it is set by
`concept_generator.py`'s own hub/front-band acceptance rate per outline, explicitly out of scope for
this Issue ("hub_guard/concept_generator's sizing machinery is explicitly out of scope" —
`concept_score.py`'s own module docstring), and by the fact that a genuinely different massing (an
L, a different outline size) is `demo/service.py`'s decision, not `run_general`'s — see
`docs/reports/concept-engine-v2-massing-multilevel-proposal.md` for how that boundary maps onto
the ROOT Issue's own "massing selection" question.

Two changes could plausibly close some of this gap, both explicitly out of THIS Issue's scope:

1. Generator/template changes that raise `_hub_concept`/`_front_band_concept`'s acceptance rate per
   outline (out of scope: "concept_generator's sizing machinery" per Issue #76's own docstring).
2. Letting Concept Engine v2 reach across `demo/service.py`'s own outline survey (out of scope:
   this Issue wires it "into `run_general`", a single-outline function by design).

## Known limitations

- The 40% diversity target (AC-2) is not met; see above. Every other Acceptance Criterion is met
  and evidenced (AC-1, AC-3 through AC-7 — see the PR's structured report for the exact test/file
  evidence).
- `plans_per_class` is bounded per-class (`_PER_CLASS_ATTEMPT_LIMIT` = 3) independently of the
  brief-wide budget; a class whose first three matching candidates all fail validation contributes
  nothing even if a fourth would have succeeded. Not measured to matter in practice (see
  Realization success), but not proven exhaustively either.
- No before/after M1-M6 comparison on the alternatives sets specifically (see Quality above).
- HUB_LOBBY, BRANCHED and RING remain unobserved in any flag-on shown plan on this corpus, same as
  the flag-off baseline — this Issue's label vocabulary (`concept_engine_v2.concept_label`) covers
  them regardless, ready for the day a generator change makes them reachable.

## Recommendation

Do not turn `CONCEPT_ENGINE_V2_ENABLED` on for production yet. The mechanism is correct, safe (zero
measured regressions across LOST/GAINED/primary_signature_changes on every corpus chunk run), and
faster or equal to the flag-off path in every timing sample taken — but it does not meet the
diversity bar the ROOT Issue set (AC-2), for a reason evidenced above to be structural rather than
an implementation gap. The owner's decision: (a) accept the mechanism as-is and lower the diversity
bar to the measured ceiling, (b) fund the generator/template work needed to raise the ceiling before
reconsidering, or (c) leave the flag off and treat this child as infrastructure for a future
Concept Engine v2 iteration once (a) or (b) is decided. This report does not choose between them.
