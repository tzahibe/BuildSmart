# `scipy` as a production dependency — integration assessment (owner item 3, 2026-10-14; assessment only, nothing changed)

**What it is needed for.** The exact sizer of the shape-agnostic realizer (`app/ai_harness/shape_agnostic/milp_oracle.py`, `milp_cells.py`) is a MILP solved by `scipy.optimize.milp`, which wraps **HiGHS** (open source, bundled in the scipy wheel — no separate solver, no licence, no network). Everything else in the realizer — embedding, envelope, realizer, validators, rendering — is pure Python + the existing `shapely`.

| question | finding |
|---|---|
| **Compatibility** | `scipy` is already resolved in `backend/uv.lock` (1.17.1 on Python 3.11, 1.18.1 on ≥ 3.12) as a transitive dependency of the `knowledge-embeddings` extra; `numpy` 2.4 is already a transitive dependency (matplotlib). Declaring `scipy>=1.11` (the `milp` API) adds nothing new to the resolution. `requires-python >= 3.11` is satisfied by every wheel. |
| **Size** | wheel 20–33 MB depending on platform (macOS arm64 20 MB, manylinux 31–33 MB); installed ≈ 78 MB. Import of `scipy.optimize` + `scipy.sparse`: ≈ 350 ms once per process (the oracle imports lazily, so a process that never sizes never pays it). |
| **Deployment impact** | there is no container or deploy manifest in the repository (the backend runs under `uvicorn` from `uv sync`); CI installs with `uv sync --group dev`, so a declared dependency is installed everywhere the suite runs. Memory: HiGHS on these models (≤ 500 constraints, ≤ 200 variables) stays in the low tens of MB. No GPU, no native build (binary wheels on every platform in the lock). |
| **Runtime** | measured on the frozen six, per exact placement incl. the inset fixed point: band oracle 15 ms–0.5 s ("area"), 0.5–3 s ("target"); cells oracle at `k=6` ≈ 0.6 s/placement (12 feasible of 20 in 12 s), at `k=12` ≈ 8 s. Per case with budgets: 10–30 s for the band family, more with every extra family. A product request must size a bounded number of candidates (the brain already realizes ≤ 12 per parti) and use the cheap feasibility screen first (15 ms) — that is the shape of a ≤ 30 s request, not a change to the solver. `time_limit` is set per solve (10 s) so a pathological model returns UNKNOWN, never hangs. |
| **Fallback** | the harness imports the oracle in a `try/except ImportError` and runs the scipy-free `solve_staircase_layout` otherwise; the brain (`run_brain`) uses production's own `solve_band_layout` today and does not touch scipy at all. So: with scipy absent the product is exactly what it is now; with scipy present the brain can offer the exact sizer and the new families behind a flag, and must fall back to the production sizer on `UNKNOWN`/import failure — explicit, typed, never silent. |
| **Risk** | version drift of HiGHS inside scipy changes solve times, not answers (an optimum is an optimum; feasibility is exact). Pin `scipy>=1.11,<2`. Determinism: HiGHS is deterministic for a fixed model and version — the corpus snapshot stays reproducible as long as the lock pins the version, which it does. |

**Recommendation (owner's decision):** declare `scipy>=1.11,<2` in `[project].dependencies` when the brain's preview is wired (item 4), not before; keep the oracle's lazy import and the typed fallback. Cost: 78 MB on disk, 0.35 s once per process, no spend. Nothing was changed by this assessment.
